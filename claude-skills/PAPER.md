# PCM 3.0：AI 代理工作流管理的設計與實踐

> 作者：shps100606-creator × Claude Code
> 撰寫時間：2026-05-18
> 版本：1.1（中文初稿，加入演進歷程）

---

## 摘要

本文記錄 PCM（Project Cycle Management）3.0 的設計動機、架構決策、實作過程與現狀評估。

PCM 3.0 是一套針對 Claude Code AI 代理設計的工作流管理框架，核心目標是解決三個在實際使用中反覆出現的問題：AI 代理跨 session 狀態斷裂、技能庫無結構路由、人機協作操作節奏不穩定。

最終架構以雙 repo 分離（claude-skills / project repo）、三段式工作流（前→中→後）、以及結構化 skill frontmatter 為主幹。設計過程中刻意否定了「建構 workflow 鏈路 runtime」與「向量語意路由層」兩個方向，讓路由邏輯留在 LLM 的原生語意匹配能力範圍內。

PCM 並非一次設計完成。它經歷了三個版本的演進，每個版本解決了前一個版本的核心問題，也帶來了新的問題，直到 3.0 才確立了以代理視角為出發點的資料架構設計原則。

---

## 1. 背景與問題

### 1.1 問題起點

Claude Code 在 web / remote session 環境下有一個結構性限制：session 之間沒有持久記憶。每次開啟新 session，代理需要重新理解當前專案狀態、可用技能、與進行中的工作。

在實際使用中，我們觀察到三個反覆出現的問題：

**問題一：工作斷裂**
代理完成部分工作後，新 session 不知道前一個 session 做了什麼、停在哪裡、下一步是什麼。重新交代背景的成本高，且容易遺漏關鍵脈絡。

**問題二：技能無結構**
隨著可用技能（skill）增加，它們以扁平、無分類的方式存放。代理沒有明確機制判斷：現在應該用哪個 skill？它的前置條件是什麼？執行後的產出是什麼？

**問題三：操作節奏不穩定**
代理傾向批次處理：一次讀取多個檔案、修改多個檔案、然後一起推送。這在實作中反覆導致 Git 衝突和操作卡住，需要人工介入解決。

## 2. 演進歷程

### 2.1 PCM 1.0 — 單一 Skill 時代

PCM 1.0 的核心是一個名為 `project-lifecycle` 的單一 skill 檔案，包含完整的 3 段 10 步作業循環。

所有邏輯完全內嵌：跨 session 重入協定（R1-R3）、每個步驟的詳細說明、各步驟的文件模板、使用者偏好設定、常見錯誤對照表，全部在同一個檔案裡。

**設計邏輯：** 自給自足。代理只需讀這一個檔案，就能執行完整的工作流。

**問題：** 這個邏輯在規模小的時候成立，但隨著工作流細節增加，單一檔案的重量快速失控。更根本的問題是：一個 skill 試圖管理整個生命週期，違反了「每個 skill 只做一件事」的原則。

| PCM 1.0 特徵 | 說明 |
|-------------|------|
| 架構 | 單一巨型 skill |
| 步驟數 | 3 段 10 步（全部內嵌）|
| 路由機制 | 無，代理依序執行 |
| skill 組織 | 扁平，無分類 |
| 主要問題 | 規模失控，難以維護 |

---

### 2.2 PCM 2.0 — 檔案屬性分類法時代

PCM 1.0 的規模問題，在 2.0 以「外包」方式解決：主體 skill（`project-cycle-management v2.0`）瘦身為一個薄型 orchestrator，每個步驟的詳細內容外包到獨立資料夾。

同時，skill 庫引入了以**數字前綴**為主的語意分類系統（檔案屬性分類法）。

**這套分類法的設計邏輯是人類中心的。** 路徑名稱對人類有直接意義，但對代理而言帶來了三個新問題：必須先讀索引才能找到 skill、新增修改需同步更新索引、11 步流程太長代理容易失向。

| PCM 2.0 特徵 | 說明 |
|-------------|------|
| 架構 | 薄型 orchestrator + 外包資料夾 |
| 步驟數 | 11 步（含分支）|
| 路由機制 | 數字前綴分類 + 路徑對照表 |
| skill 組織 | 語意分類（10/20/30/40 前綴）|
| 主要問題 | 索引維護成本高；11步太長，代理容易失向 |

---

### 2.3 從 2.0 到 3.0 的核心轉變：從人類中心到代理中心

PCM 3.0 的核心問題意識是：**如果資料結構直接以代理的閱讀方式設計，中間層是否可以消除？**

答案是可以。方法是把路由資訊嵌入每個 skill 的 frontmatter：代理讀到 frontmatter，就知道這個 skill 在什麼情況下觸發、前置條件是什麼、產出是什麼、在三段式工作流中扮演什麼角色。不需要查索引，不需要讀路徑對照表。

| 比較維度 | 2.0（檔案屬性分類法）| 3.0（代理中心設計）|
|---------|-------------------|------------------|
| 路由資訊位置 | 主體 skill 的路徑對照表 | 每個 skill 的 frontmatter |
| 代理讀取路徑 | 讀索引 → 找路徑 → 讀 skill | 直接讀 frontmatter |
| 維護成本 | 新增/修改 skill 需更新索引 | frontmatter 與 skill 同步 |
| PCM 的角色 | 目錄 + orchestrator | 統攝所有 skill 的 meta-skill |
| 流程長度 | 11 步 | 3 段（前→中→後）|

## 3. 設計理念

### 3.1 三個核心原則

**原則一：結構優於約定**

任何「代理應該知道的規則」都必須寫在代理 session 啟動時會讀到的位置，不能依賴對話歷史或口頭約定。

**原則二：漸進式揭露（Progressive Disclosure）**

代理不應在每個 session 開始時讀取所有 skill 的完整內容。Frontmatter 提供路由所需的最小資訊，完整 body 只在確認要使用時才讀取。

**原則三：不建構 runtime**

工作流鏈路是文件化的架構提示，不是執行期的路由機制。LLM 在讀取 `trigger.match` 時已具備語意匹配能力。

### 3.2 三段式工作流

```
前（環境確認 / 接手前一個 session 的狀態）
  ↓
中（Iteration 迴圈）  ←── exit condition: Milestone 達成
  ↓
後（審查 / 萃取 / 封存）
```

| 路線 | 適用情境 | 走法 |
|------|---------|------|
| 路線 A | 有實作，需要迭代 | 前 → 中 → 後A |
| 路線 B | 純規劃，無實作 | 前 → 後B（跳過中）|

## 4. 架構設計

### 4.1 雙 Repo 架構

```
claude-skills repo              project repo（e.g., line-crm-platform）
────────────────────            ──────────────────────────────────────
HOW（通用技能庫）                WHAT / WHERE（專案脈絡）
steps/前/skills/                CLAUDE.md（固定參數、環境路徑）
steps/中/skills/                _docs/（版本、審查、路線圖）
steps/後/skills/                src/（實際程式碼）
PCM.md（工作流說明）
CLAUDE.md（代理行為守則）
```

### 4.2 結構化 Skill Frontmatter

```yaml
---
name: skill-name
trigger:
  match:
    - "觸發詞"
  not_match:
    - "不適用情境 → 見 other-skill"
preconditions:
  - "必要條件"
context_inputs:
  VAR_NAME: "資料來源說明"
context_outputs:
  - "執行後產出"
workflow:
  after: ["前置 skill"]
  before: ["後續 skill"]
  role: "executor"
  # role 可選值: precondition-builder | executor | verifier | archiver
---
```

## 5. 評估

### 解決了什麼

- **工作斷裂**：雙 CLAUDE.md + 版本文件的組合，讓新 session 能在幾分鐘內重建工作脈絡
- **技能無結構**：Frontmatter 提供可掃描的路由資訊
- **操作節奏**：「一個一個做，一個一個推」寫入 CLAUDE.md 後，批次操作導致的卡住次數顯著減少
- **索引維護問題**：Frontmatter 與 skill 同步，消除了 2.0 時代的索引不一致問題

### 沒有解決什麼

- **Session 接手仍需人工確認**：代理不會自動知道「從哪裡開始」
- **Skill 品質不均**：21 個 skill 的 body 品質差異較大
- **無法防止代理偏離**：規則在 CLAUDE.md 中，但代理仍可能在長 session 中忽略規則

---

## 6. 結論

PCM 3.0 是一個「夠用就好」設計的實例。三個版本的演進揭示了一個核心洞見：**AI 代理的工作流架構，應該以代理的閱讀方式為設計出發點，而不是讓代理去適應人類習慣的資料組織方式**。

最重要的技術選擇是：**在 LLM 原生能力能解決的地方，不建構 runtime**。
